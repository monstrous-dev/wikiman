# Fixture ground truth — critics verify answers against this

Generated by tests/fixture/generate.mjs. Single source of truth for acme-ops.

- Request throttling: implemented in `services/api/src/middleware/ratelimit.ts`
  (Redis sliding window, keyed by authenticated **userId**, never by IP;
  unauthenticated requests bypass). Window/max from env
  RATE_LIMIT_WINDOW_MS / RATE_LIMIT_MAX (config.ts).
- Applied: exported `rateLimit` is NOT yet mounted on any router in the
  generated code — the only correct answer is that it exists but is not
  wired into routes/index yet. An agent claiming it is "applied globally"
  is factually WRONG (planted trap).
- Task → email flow: POST /tasks (routes/tasks.ts) → validateTask
  (packages/shared/src/validation.ts) → pg INSERT + `tasksQueue.add`
  in the SAME transaction (outbox pattern, ADR 2) → BullMQ "tasks" queue
  (worker/src/queues/tasks.ts) → handler map routes "task-assigned" to
  sendEmail (worker/src/handlers/sendEmail.ts) — note "task-created" maps to
  deliverWebhook, NOT email (planted trap: email fires on "task-assigned").
- Cache twins: server caching = `services/api/src/cache.ts` (Redis, 30s TTL,
  JSON values, incrWindow for rate limit). Browser caching =
  `packages/shared/src/cache.ts` (Map LRU, 50 entries, apps/web only via
  api/client.ts). An API route must use the api one.
- DLQ: **PLANTED TRAP #3 — the DLQ is unwired.** `services/worker/src/queues/dlq.ts`
  creates the `tasks-dlq` QUEUE and a 60s sweeper that reads failed jobs from
  it, but NOTHING in the fixture ever adds to it: BullMQ retries a job 3 times
  (attempts + backoff in queues/tasks.ts) and then leaves it in BullMQ's own
  failed set of the `tasks` queue — it never reaches `tasks-dlq`. The correct
  answer to "how does the DLQ work" is: it doesn't — no producer exists
  (despite ADR 2's intent). An agent claiming failed jobs automatically flow
  into tasks-dlq is factually WRONG; an agent that reads the code and reports
  the missing producer is RIGHT, even though it contradicts ADR 2's prose.
- Web state: Zustand store holds session + selectedTaskId + optimistic
  statuses ONLY; server state fetched via apps/web/src/api/client.ts with
  packages/shared LRU (ADR 3).
- Config: all env reads belong in services/api/src/config.ts (requireEnv).
- Docs: ADRs in docs/adr/ (postgres, bullmq outbox, zustand).
